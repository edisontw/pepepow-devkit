# PEPEW Payment URI v1

Status: **v1 specification**

## 1. Purpose

PEPEW Payment URI v1 defines a small, wallet-facing URI format for requesting a PEPEW payment.

It carries public payment intent only. It does not carry wallet recovery material, signing keys, webhook secrets, API credentials, or private infrastructure endpoints.

Canonical form:

```text
pepew:<address>?amount=<amount>&label=<label>&message=<message>
```

Only the address is required.

## 2. Scheme

The URI scheme is:

```text
pepew
```

URI schemes are parsed case-insensitively. Serializers MUST emit lowercase `pepew:`.

An authority component is not used. Therefore this is valid:

```text
pepew:PRfbEeHAKKbz6Voz85WJudrJwTA3ZbHunb
```

and this is invalid:

```text
pepew://PRfbEeHAKKbz6Voz85WJudrJwTA3ZbHunb
```

Fragments (`#...`) are not part of v1 and MUST be rejected.

## 3. Address

The path component is a literal PEPEPOW P2PKH Base58Check address.

For current PEPEPOW mainnet:

```text
P2PKH version byte: 0x37
payload: 0x37 || HASH160(pubkey)
Base58Check checksum: required
display addresses currently begin with P
```

Implementations MUST validate the decoded version byte and checksum. They MUST NOT validate only by checking the first displayed character.

Known fixture used by the current PEPEW Light backend:

```text
PRfbEeHAKKbz6Voz85WJudrJwTA3ZbHunb
```

Percent-encoded addresses are not used in v1.

## 4. Amount

`amount` is optional.

When present it represents PEPEW, not atomic units.

PEPEW uses 8 decimal places:

```text
1 PEPEW = 100000000 atomic units
```

Accepted grammar:

```text
amount = whole [ "." fraction ]
whole = "0" / nonzero-digit *DIGIT
fraction = 1*8DIGIT
```

Rules:

- amount MUST be greater than zero
- at most 8 fractional digits
- no sign
- no exponent notation
- no thousands separators
- no whitespace
- parsers SHOULD convert using integer/decimal arithmetic rather than binary floating point

Examples:

```text
1
12.34
0.00000001
```

Invalid examples:

```text
0
-1
1e-8
0.000000001
```

Canonical serializers remove unnecessary trailing fractional zeros.

## 5. Human-facing parameters

### `label`

Optional UTF-8 text identifying the recipient or merchant.

### `message`

Optional UTF-8 text describing the payment, order, or invoice.

These values are display data, not authenticated merchant identity. Wallets MUST treat them as untrusted text and MUST NOT render them as executable HTML.

Query components use UTF-8 percent encoding. Canonical serializers use `%20` for spaces.

## 6. Extension parameters

Unknown optional parameters MAY appear.

A v1 parser SHOULD preserve or ignore unknown optional parameters without changing the meaning of known fields.

Parameter names beginning with:

```text
req-
```

are required extensions. A parser that does not implement a required extension MUST reject the URI.

v1 defines no `req-*` parameters.

Known parameter names are lowercase and case-sensitive:

```text
amount
label
message
```

Case variants such as `Amount` MUST NOT be interpreted as `amount`.

Duplicate query parameter names are invalid.

## 7. Canonical serialization

Canonical parameter order is:

1. `amount`
2. `label`
3. `message`
4. unknown optional parameters sorted lexicographically by name

Canonical serializers:

- emit lowercase `pepew:`
- emit the original validated Base58Check address
- normalize `amount`
- percent-encode query names and values
- use `%20` rather than `+` for spaces
- omit the `?` when no query parameters exist

Example:

```text
pepew:PRfbEeHAKKbz6Voz85WJudrJwTA3ZbHunb?amount=12.34&label=Coffee%20Shop&message=Order%201234
```

## 8. Error handling

Parsers MUST reject at least:

- missing or different scheme
- missing address
- invalid Base58Check checksum
- unsupported address version
- authority form (`pepew://...`)
- fragments
- invalid or non-positive amounts
- amounts with more than 8 decimal places
- duplicate parameter names
- malformed percent encoding
- unsupported `req-*` parameters

## 9. Security and privacy

A Payment URI is public payment intent.

It MUST NOT contain:

- mnemonic / seed phrase
- private key
- wallet password
- signed or unsigned private wallet state
- webhook secret
- merchant API secret
- private ElectrumX address
- RPC credentials

Wallets SHOULD show the destination address and amount for user review before signing.

The URI itself does not authenticate a merchant. Applications requiring authenticated invoices must provide that property at a higher protocol layer.

## 10. Compatibility and versioning

v1 intentionally has no explicit `version=` query parameter.

Backward-compatible optional fields can be added as ordinary optional parameters. Features that are mandatory for correct payment interpretation use the `req-*` convention so older parsers fail safely.

A future incompatible redesign requires a new specification version and MUST define an explicit migration strategy rather than silently changing v1 semantics.

## 11. Test vectors

Machine-readable vectors are maintained at:

```text
test-vectors/payment-uri-v1.json
```

Implementations should pass the shared vectors before claiming PEPEW Payment URI v1 compatibility.
